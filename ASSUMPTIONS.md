# Assumptions

Decisions made where the specification leaves room for interpretation, as the task asks.
How to run and use the application is described in [README.md](README.md).

## Lifecycle

- `DELETED` is a state, not a physical delete: the request stays in the database and appears in the list.
- A reason is stored only for `DELETE` and `REJECT`; if sent with other actions, it is ignored.
- `name` cannot be changed after creation; only `body` is editable, as the specification describes.
- If an action is both not allowed in the current state and missing its reason, the state error (`409`) wins.

## Validation

- Validation happens in two places: Bean Validation on the DTOs gives the API client a list of all invalid
  fields at once, and the domain enforces its own invariants independently of the caller.
- Values are stored as sent; trimming whitespace is the client's responsibility.
  Blank values (empty or whitespace only) are rejected.
- Limits: `name` up to 255 characters, `body` up to 10,000 characters. The specification does not define
  a maximum for the content; the limit protects the API and the size of its responses. The limits are defined
  once in the domain (`Request.MAX_NAME_LENGTH`, `Request.MAX_BODY_LENGTH`) and reused by the DTO validation.
- A page of the list has a bounded size: at most `max-size` summaries, each without the body and with a name
  of at most 255 characters, so browsing stays cheap however large the bodies are.

## Publication number

- Generated from a PostgreSQL sequence, so it is unique also with several application instances.
- The number is requested only after the transition is validated, so a rejected `PUBLISH` does not consume one.
- Numbers are unique but not guaranteed to be consecutive: a transaction rolled back after taking a number
  (e.g. on a concurrent modification) leaves a gap. The specification asks for uniqueness only.

## Audit log

- The history records state changes only: creation is captured by `createdAt`, and body edits are not
  state changes.
- History entries are part of the `Request` aggregate (no identity of their own) and are append-only.

## Browsing

- The name filter is a case-insensitive "contains" match; `%` and `_` in the searched text are matched literally.
- The specification does not say which fields the list should contain. It returns summaries without the body:
  a body can be up to 10,000 characters, so including it would make a page of up to 100 requests very large
  for a view that is only used to browse and find requests. The full request, with its body, is available from
  `GET /api/requests/{id}`.
- Results are ordered from newest to oldest (`createdAt`, then `id` for a stable order); indexes match this order.
- A requested page size above `max-size` is reduced to `max-size`.
- A "contains" search (`lower(name) LIKE '%...%'`) cannot use a B-tree index, because the pattern is not
  anchored at the start. The name filter is therefore backed by a trigram index: a `pg_trgm` GIN index on
  `lower(name)`, the same expression the query uses. `pg_trgm` is a standard PostgreSQL extension
  ([documentation](https://www.postgresql.org/docs/current/pgtrgm.html)).
- With little data PostgreSQL still chooses a full table scan, which is cheaper than using the index at that size.
  The index is there for when the number of requests grows: without it, filtering by name would scan the whole
  table. It costs little here, because a name is written once and never changes. Search terms shorter than
  three characters gain little from trigrams.

## Concurrency

- Requests are protected with optimistic locking (`@Version`): when two clients change the same request at once,
  one of them gets `409 Conflict` and can retry.

## Technical

- The domain service uses Spring's `@Service` and `@Transactional` as a pragmatic trade-off; the domain model
  itself (aggregate, state machine, history) is framework-free and tested without Spring.
- Timestamps come from `Instant.now()` instead of an injected `Clock`: they are informational and no business
  rule depends on time, so tests do not need to control it.
- Request ids are UUIDs generated by the application; the publication number is a separate field.
- The concurrent-modification error comes from Spring's data access abstraction and is handled in the web
  layer: the conflict is detected when the transaction commits, outside the repository adapter.
- Every error is logged at ERROR in one format, with the HTTP method and path. Client errors (4xx) are logged
  with their reason only, server errors (5xx) also with the stack trace.

## Testing

- Unit tests run without external infrastructure (no database, no Docker); everything that needs PostgreSQL
  is in the separate `integration` source set and runs on a real database via Testcontainers.
- The service tests use a hand-written in-memory implementation of the `RequestRepository` port instead of mocks:
  the tests check the resulting state rather than which repository methods were called, so they stay short
  and do not break when the service is refactored. Mocks are used where the interaction itself is what is tested
  (the web-layer slice test mocks the service).
